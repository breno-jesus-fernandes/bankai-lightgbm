# AGENTS.md

Rules for every contributor, human or AI agent, working on **bankai-lightgbm**: a Rust rewrite of
[LightGBM](https://github.com/lightgbm-org/LightGBM) with a drop-in Python package.

## 1. Goals (non-negotiable)

1. **Feature parity** with upstream LightGBM, pinned in [`UPSTREAM_VERSION`](UPSTREAM_VERSION) (currently `v4.7.0`).
   CPU parity is the v1.0 target. CUDA and distributed training come later, behind cargo features. See [`ROADMAP.md`](ROADMAP.md).
2. **Speed equal to or faster than upstream** on the same hardware, threads, and params.
3. **Model compatibility in both directions:** model text files and JSON dumps load in either library and give identical predictions.
4. **Drop-in Python API:** `import bankai_lightgbm as lgb` works wherever `import lightgbm as lgb` works. Requires **Python >= 3.11**.

## 2. Source of truth

- The upstream C++ code at the pinned tag is the spec. When behavior is unclear, read upstream (`src/`, `include/LightGBM/`) and match it, quirks included.
- When you port non-obvious behavior, cite the upstream code in a doc comment, for example
  `// upstream: src/treelearner/feature_histogram.hpp (v4.7.0) GetSplitGains`.
- Lay out modules to mirror upstream's `src/` directories (`io/`, `treelearner/`, `boosting/`, `objective/`, `metric/`) so reviewers can compare side by side.
- Bumping `UPSTREAM_VERSION` is its own PR. That PR regenerates fixtures and lists every upstream change in `ROADMAP.md`.

## 3. TDD first, always

Every change follows **red → green → refactor**:

1. **Red:** write a test that fails for the right reason. Run it and watch it fail.
2. **Green:** write the minimum code to make it pass.
3. **Refactor:** clean up while the tests stay green.

Rules:
- Do not merge behavior that lacks a test which failed first.
- Every bug fix starts with a regression test that reproduces the bug.
- When porting an upstream feature, write the **parity test** first (Section 4). It is the acceptance test.
- Never delete or weaken a test just to make CI pass. Any change to a tolerance needs a written justification in the test.

## 4. Test layers

| Layer | Tool | Location | What it covers |
|---|---|---|---|
| Unit | `cargo test` | `#[cfg(test)] mod tests` next to the code | Pure functions: split gain, bin search, objective gradients |
| Property | `proptest` | crate `tests/` | Binning invariants, serialization round-trips, histogram subtraction |
| Parity | `pytest` | `tests/parity/` | Same data and params in `lightgbm==4.7.0` and `bankai_lightgbm`, with outputs compared |
| Golden | `cargo test` + `tests/fixtures/` | | Upstream-produced models and predictions, generated by `scripts/gen_fixtures.py` |
| Fuzz | `cargo-fuzz` | `fuzz/` | Model text, JSON, CSV, and LibSVM parsers never panic |
| Upstream suite | `pytest` | `tests/python_package_test/` (ported) | Upstream's Python tests run against `bankai_lightgbm` |

### Parity tolerances
- **Predicting with an upstream model file:** must match bit-exactly. A difference of at most 1 ULP is allowed only where upstream itself is non-deterministic.
- **Training with `deterministic=true, num_threads=1, seed=<fixed>`:** tree structure must be identical (features, thresholds, leaf counts). Leaf values must match within `rtol=1e-12`.
- **Multithreaded training:** prediction `rtol=1e-6`, and metric values within `1e-6`.
- **Bit-exactness is platform-specific.** Upstream's rounding depends on how its compiler built each wheel. FMA contraction and auto-vectorized reductions both change the last bits. Golden fixtures record their platform in `tests/fixtures/platform.json`. Tests require bit-exact results only on that platform, and allow ≤64 ULP elsewhere (`tests/support::assert_bits_eq`).
- To reproduce upstream rounding, use `utils::common::madd` wherever upstream writes `x += a * b`. It is fused on aarch64, as clang does. When parity is off by a few ULPs, disassemble upstream's `lib_lightgbm` (`otool -tV` / `objdump -d`) before guessing. Example: `Tree::ExpectedValue` is vectorized in blocks of 16 (unfused) with a fused scalar tail on macOS/arm64.
- Upstream has two float parsers: `StringToArray` (precise, `fast_double_parser`) and `StringToArrayFast` (legacy `Common::Atof`, *not* correctly rounded). Port each call site with the same parser. Today, prediction only depends on the precise fields.
- Never compare fixtures with `==` on floats in Python. Use `np.testing.assert_allclose` with the documented tolerance, or `assert_array_equal` for bit-exact cases.

## 5. Performance is a requirement

- Measure before optimizing. Profile with `cargo flamegraph` or `samply`, and attach the findings to the PR.
- Any PR that touches a hot path (histograms, split finding, data partition, prediction, binning) must include `criterion` results before and after.
- CI gates:
  - A `criterion` regression of more than **5%** vs `main` fails the build.
  - The Python-level benchmark (`benches/`) runs subsets of Higgs, Epsilon, MSLR/Yahoo LTR, and a sparse dataset. It compares against upstream `lightgbm==4.7.0`. Being slower than upstream by more than run-to-run noise (~3%) fails the build.
  - The interleaved benchmark job in CI runs on pushes to `main`, on manual runs, and on pull requests that touch hot-path code (`treelearner/`, `boosting/`, `objective/`, `io/bin*`, `io/sparse.rs`, `io/sample.rs`, `predictor.rs`, `tree.rs`, `utils/spin_pool.rs`, `utils/common.rs`, the benchmark scripts, and `ci.yml`). Other pull requests skip it. Edit the `changes` filter in `.github/workflows/ci.yml` when a new hot path appears.
- Parallelism uses `rayon` (instead of OpenMP). Respect `num_threads`: build a scoped thread pool per Booster rather than the global pool.
- SIMD uses `std::arch` with runtime feature detection (`is_x86_feature_detected!`), or `pulp`. A scalar fallback must exist and be tested.
- Avoid allocating in inner loops. Reuse buffers through the per-learner state, as upstream's `TrainingShareStates` does.

## 6. Rust practices

- Pin the stable toolchain in `rust-toolchain.toml`. Edition 2024.
- `cargo fmt --all` and `cargo clippy --workspace --all-targets -- -D warnings` must be clean.
- `unsafe_code` is denied workspace-wide (`[workspace.lints.rust]`). `unsafe` is allowed only in modules on the allowlist (`histogram`, `simd`, `capi`, `python` FFI, `utils::spin_pool`: the persistent worker pool for training's parallel regions; other modules reach it only through its safe API), opted in with `#[allow(unsafe_code)]` on the module declaration. Every `unsafe` block needs a `// SAFETY:` comment, and these modules run under `cargo miri test`.
- No `unwrap()`, `expect()`, or `panic!` in library code outside tests. Return `Result` with errors defined via `thiserror`. Panics must never cross the FFI boundary (`catch_unwind` in `lgbm-capi` and `lgbm-python`).
- Numeric types match upstream exactly: `f64` scores and gradients where upstream uses `double`, and `f32` (`score_t`/`label_t`) where upstream does. Bin indices use the same widths (u8/u16/u32, plus the 4-bit packed form).
- Public items have doc comments. Prefer small modules and plain functions over deep trait hierarchies. Use static dispatch (generics) in hot paths and `dyn Trait` only at config-selected boundaries (objective, metric, boosting type).

## 7. Python practices

- `requires-python = ">=3.11"`. Build with **maturin** + **PyO3** (`abi3-py311`).
- Manage environments with `uv`. Lint with `ruff check` and `ruff format`. Type-check with `mypy --strict` on `python/bankai_lightgbm`.
- The public API mirrors `lightgbm` names, signatures, defaults, warnings, and exceptions (`LightGBMError`): `Dataset`, `Booster`, `train`, `cv`, `LGBMModel`, `LGBMClassifier`, `LGBMRegressor`, `LGBMRanker`, the callbacks, and the plotting helpers.
- Accept numpy, pandas, scipy.sparse, and pyarrow inputs. Use zero-copy where the memory layout allows it.

## 8. Compatibility rules

- Model text and JSON output must round-trip with upstream. Never "improve" the format.
- Every parameter supports all upstream aliases. The parameter table is generated from upstream's `include/LightGBM/config.h` and is not edited by hand.
- A parameter or feature that is not supported yet raises a clear error (`NotImplementedError` in Python, `Error::Unsupported` in Rust). Never ignore a parameter silently.

## 9. Workflow

- **Commit early, commit often:** commit each green step (test + implementation) as soon as it passes. Never leave work uncommitted at the end of a session.
- Run `scripts/check.sh` before every commit. It runs fmt, clippy, cargo test, ruff, mypy, maturin and pytest, and must end with `all green`. Optionally, enable it as a pre-commit hook in your own clone.
- **Always push:** after every commit, `git push` the branch to GitHub (`origin`) so no progress is local-only. Work on a feature branch (e.g. `p1-predict`), never commit directly to `main`. Merge to `main` through a PR.
- Never commit a red build. If a step is not green yet, keep it out of the commit (or mark the test `#[ignore]`/`xfail` with a reason that points to the roadmap item).
- Keep PRs small, with one feature or one fix each. Use Conventional Commits (`feat(core): ...`, `fix(io): ...`, `perf(treelearner): ...`, `test(parity): ...`).
- Tick the matching checkbox in `ROADMAP.md` in the same PR.
- Update `CHANGELOG.md` for user-visible changes.

## 10. Definition of done

- [ ] Tests written first, failed first, and now green
- [ ] Parity test added or extended (for features that have an upstream equivalent)
- [ ] Benchmarks show no regression (for hot-path changes)
- [ ] `fmt`, `clippy`, `ruff`, and `mypy` clean
- [ ] Docs, `ROADMAP.md`, and `CHANGELOG.md` updated

## 12. How tests and benchmarks are run

### Build profile (read this before any timing)
- **Benchmarks use a release build only.** Python timings require `maturin develop -r`. Rust timings require `cargo bench` or `cargo test --release`.
- `scripts/check.sh` installs a **debug** build of the Python package. After running it, rebuild with `maturin develop -r` before measuring anything.
- Before reporting a Python timing, confirm the installed build: the `.so` under `python/bankai_lightgbm/` must be newer than `target/release`, and must not be newer than `target/debug` from a later check run. If in doubt, rebuild.
- Every reported number must record: build profile, `num_threads`, upstream version (`lightgbm==4.7.0`), `OMP_WAIT_POLICY` for upstream runs, data shape, and the commit hash.

### Comparing with upstream
- Run bankai and `lightgbm==4.7.0` in the same venv, on the same data, with the same params and the same `num_threads`.
- Compare only within one session. Numbers from different sessions or machine states are not comparable.

### Measuring on a noisy machine
- The development VM has 2 vCPUs and ±20–30% run-to-run noise.
- Interleave the runs (A, B, A, B, …) over at least 7 rounds, and report medians. Best-of-N alone is not enough.
- A single-run difference below about 3% is noise (the AGENTS.md CI threshold).
- For micro-measurements, repeat the call many times per timed block so each block lasts at least a few milliseconds.

### Where tests live
- Unit: `#[cfg(test)]` modules next to the code, run with `cargo test --workspace`.
- Integration: `crates/*/tests/`. Thread invariance (`crates/lgbm-core/tests/thread_invariance.rs`) must pass for 1, 2 and 3 threads. Compare only the tree section of the model text, because the trailing `parameters:` block echoes `num_threads`.
- Parity: `pytest tests/parity` against `lightgbm==4.7.0`.
- Criterion: `cargo bench -p lgbm-core`. For any hot-path change, record before and after results on the same machine, and the change must stay within the 5% gate.

### Experiments
- Throwaway timing tests live outside the repository (the session scratchpad). Do not commit them, and do not leave untracked files in the repo.
- A test used only for investigation is marked `#[ignore]` and run with `cargo test --release -- --ignored --nocapture`. If it is worth keeping, convert it into a criterion benchmark or a proper test first.
- Results from an experiment go into the PR or CHANGELOG notes with the commands used to reproduce them.
