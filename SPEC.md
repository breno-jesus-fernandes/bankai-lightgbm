# SPEC: technical contract for bankai-lightgbm

This file states decisions, not options. An agent that hits a question this file answers
follows the rule and does not ask. A question it does not answer goes to `DECISIONS.md`
(see AGENTS.md section 13). Rule IDs (`SPEC-<AREA>-<n>`) are cited in code comments and in
`DECISIONS.md`.

Upstream is the spec. The pinned tag is in `UPSTREAM_VERSION` (`v4.7.0`). When this file
and upstream disagree, upstream wins, quirks included, and the disagreement is recorded here.

## 1. Scope and oracle

- **SPEC-SCOPE-1.** The oracle is the `lightgbm==4.7.0` wheel plus the upstream C++ source at
  the pinned tag. Parity tests compare against the wheel. Golden fixtures are generated from
  the wheel by `scripts/gen_*.py`.
- **SPEC-SCOPE-2.** No upstream C/C++ is compiled or linked into bankai. `third_party/lightgbm/config.h`
  is an input to `scripts/gen_config.py` only.
- **SPEC-SCOPE-3.** Fixture bit-exactness is defined only on the platform in
  `tests/fixtures/platform.json`. Other platforms use the tolerances in section 5.

  doc comment, for example `// upstream: src/treelearner/feature_histogram.hpp (v4.7.0) GetSplitGains`.

- **SPEC-MAP-3.** Native code is reached from Python only through `bankai_lightgbm._lib` (PyO3).
  Python code never calls into Rust through ctypes.

## 3. Memory and concurrency

### Memory

- **SPEC-MEM-1.** `std::vector<T>` maps to `Vec<T>`. Upstream raw-pointer views map to slices with
  explicit offsets. Do not introduce `ndarray` into the core: upstream's layouts are flat buffers
  and slices express them with no extra dependency.
- **SPEC-MEM-2.** Numeric widths match upstream exactly: `double` is `f64`, `float` (`score_t`,
  `label_t`) is `f32`, bin indices are `u8`/`u16`/`u32` plus the 4-bit packed form.
- **SPEC-MEM-3.** `unsafe` is permitted only in the allowlisted modules in AGENTS.md section 6, with
  a `// SAFETY:` comment on each block.
- **SPEC-MEM-4.** Inner loops do not allocate. Buffers live in per-learner state, as upstream's
  `TrainingShareStates` does.
- **SPEC-MEM-5.** Custom allocators are not ported. Upstream's allocation is not part of the
  behaviour being matched.

### Concurrency

- **SPEC-CONC-1 (locked 2026-11-08).** Parallel loops use `rayon`, not `spin_pool`. Upstream's
  OpenMP regions map to rayon scopes. Each Booster owns one scoped `rayon::ThreadPool` sized from
  `num_threads`. The global pool is never used for training.
- **SPEC-CONC-2.** Reductions are deterministic. A parallel reduction splits work into fixed chunks,
  computes one partial per chunk, and merges partials in chunk-index order. Completion order is never
  observed. This keeps results identical across thread counts (`thread_invariance` gate).
- **SPEC-CONC-3.** Histogram construction keeps upstream's block and merge order (see SPEC-NUM-6), so
  it is independent of how many threads run the blocks.
- **SPEC-CONC-4.** Nested parallel regions are not allowed. A parallel call inside a parallel region
  runs serially.
- **SPEC-CONC-5 (migration).** `utils::spin_pool` remains the implementation until the migration node
  `spin_pool -> rayon` in PROGRESS.md lands. Its gate: no interleaved-benchmark slowdown above 3%
  against the current code, thread scaling not worse than the current ~1.2x on 2 threads, and
  `thread_invariance` passing for 1, 2 and 3 threads. If the gate is missed, the failure goes to
  `DECISIONS.md` and the gate is not relaxed.
- **SPEC-CONC-6.** SIMD uses `std::arch` with runtime detection (`is_x86_feature_detected!`) or `pulp`.
  A scalar fallback exists and is tested. Results must match the scalar path bit for bit on the
  fixture platform.

## 4. Numerical contract

- **SPEC-NUM-1 (prediction).** Prediction from an upstream model file is bit-exact on the fixture
  platform. Off-platform, up to 64 ULP is allowed (`tests/support::assert_bits_eq`).
- **SPEC-NUM-2 (training, deterministic).** With `deterministic=true, num_threads=1, seed=<fixed>`, tree
  structure is identical (features, thresholds, leaf counts). Leaf values match at `rtol=1e-12`.
- **SPEC-NUM-3 (training, multi-threaded).** Predictions match at `rtol=1e-6`. Metric values match
  within `1e-6`.
- **SPEC-NUM-4 (bin mappers).** Bin boundaries are bit-exact with upstream on the fixture platform
  (`tests/fixtures/train/*`, `datasets/*`). Off-platform, the same 64 ULP bound applies.
- **SPEC-NUM-5 (split gain).** Split gains are computed in `f64` as upstream does. A gain tie is broken
  by the rule in SPEC-NUM-7. Pinned by D-005: gains are compared with upstream's `SplitInfo::operator>`
  (`src/treelearner/split_info.hpp`, v4.7.0), exact `f64` comparison, no tolerance; the NaN check is
  upstream's always-false `gain == NAN`, reproduced on purpose. Tested by `tests/parity/test_split_tie_parity.py`.
- **SPEC-NUM-6 (accumulation order).** Wherever upstream writes `x += a * b`, bankai uses
  `utils::common::madd` so the rounding matches upstream's compiled code (fused on aarch64). Histogram
  sums accumulate rows in leaf order, within each bin, as the column-wise and row-wise kernels both do.
- **SPEC-NUM-7 (tie-breaking).** Equal gains: the lower feature index wins, `-1` counts as the largest. Confirmed
  against upstream `SplitInfo::operator>` (D-005) and pinned by `tests/parity/test_split_tie_parity.py`.
- **SPEC-NUM-8 (float parsing).** Upstream has two parsers. `StringToArray` uses the precise
  `fast_double_parser` path and `StringToArrayFast` uses the legacy `Common::Atof`, which is not correctly
  rounded. Each call site ports with the same parser. Prediction-relevant fields use the precise parser.
- **SPEC-NUM-9 (RNG).** Random numbers come from `utils::random`, a port of upstream's `Random` (LCG,
  seeded as upstream seeds it per use site, e.g. `Random(17)` for DART). The `rand` crate is not used in
  any training or prediction path. Each use site documents its seed derivation with an upstream citation.
- **SPEC-NUM-10 (known upstream undefined behaviour).** Where upstream reads uninitialised memory, bankai
  either reproduces the majority outcome and records it in `DECISIONS.md`, or refuses with `Unsupported`.
  Current cases: DART's first drop draw (`is_update_score_cur_iter_`), monotone `advanced` with categorical
  features (refused).
- **SPEC-NUM-11 (tolerances in tests).** Any tolerance wider than the table above needs a justification
  comment in the test, citing the cause. Tolerance edits are governed by AGENTS.md section 13.

## 5. Platform and tolerances summary

| Check | Tolerance | Where |
|---|---|---|
| Model file predict | bit-exact (fixture platform); ≤64 ULP elsewhere | SPEC-NUM-1 |
| Deterministic training, 1 thread | structure identical; leaves `rtol=1e-12` | SPEC-NUM-2 |
| Multi-thread training | predict `rtol=1e-6`; metrics `1e-6` | SPEC-NUM-3 |
| Bin boundaries | bit-exact (fixture platform) | SPEC-NUM-4 |
| Row-wise vs column-wise | model text byte-identical | `test_row_wise_training_parity.py` |

## 6. Errors and API boundary

- **SPEC-ERR-1.** Library code returns `Result<T, lgbm_core::Error>`. `Error` is a `thiserror` enum with
  the variants `InvalidParameter`, `Unsupported`, `Parse`, `BinaryOpen`, `BinaryWrite`, `Io`. No variant
  wraps an upstream error code.
- **SPEC-ERR-2.** Upstream's `Log::Fatal` and thrown `std::runtime_error` become `Error` values. The message
  text matches upstream where a Python test checks it.
- **SPEC-ERR-3.** Python maps `Error::InvalidParameter`, `Parse`, `BinaryOpen`, `BinaryWrite`, `Io` to
  `LightGBMError`. `Error::Unsupported` maps to `NotImplementedError` (AGENTS.md section 8).
- **SPEC-ERR-4.** Every FFI entry point (`lgbm-python`, and `lgbm-capi` when it exists) wraps the call in
  `catch_unwind`. A panic becomes `LightGBMError` at the Python boundary. It never becomes
  `PanicException`. This is a known gap, tracked in PROGRESS.md (Tier 1).
- **SPEC-ERR-5 (C API).** `lgbm-capi` returns the upstream `c_api.h` convention: `0` for success, `-1` for
  failure, and the message in a thread-local last-error buffer read by `LGBM_GetLastError`.
- **SPEC-ERR-6.** Parameters that bankai does not implement raise. They are never silently ignored
  (AGENTS.md section 8).

## 7. Python boundary

- **SPEC-PY-1.** Dense numpy input: `float64` C-contiguous is borrowed with no copy. Other dtypes or
  layouts are converted once, in Python, before crossing into Rust. `float32` and column-major input
  are handled natively where the native layer supports them (PROGRESS.md Tier 5 tracks removing the
  remaining float64 copy).
- **SPEC-PY-2.** Sparse input (CSR/CSC) is passed as the three index and value arrays. Other scipy formats
  are converted with upstream's warning text.
- **SPEC-PY-3.** Pandas, pyarrow and polars are handled in Python through narwhals and `take`. The native
  layer receives numpy arrays only.
- **SPEC-PY-4.** The GIL is released (`py.allow_threads`) around every native call that does training or
  prediction work. Native code never calls back into Python except through the explicit custom objective
  and metric hooks.
- **SPEC-PY-5 (names and signatures).** The public API mirrors `lightgbm==4.7.0` names, signatures,
  defaults, warning text and exception types (`Dataset`, `Booster`, `train`, `cv`, `LGBMModel`,
  `LGBMClassifier`, `LGBMRegressor`, `LGBMRanker`, callbacks, plotting). A difference is a bug.

## 8. Unsupported features and the registry

- **SPEC-UNS-1.** A parameter or feature bankai does not implement raises `Unsupported` in Rust and
  `NotImplementedError` in Python, with a message that names the feature and the ROADMAP item.
- **SPEC-UNS-2.** Upstream tests that fail on a known gap are listed in `tests/known_upstream_gaps.tsv`
  (`nodeid<TAB>reason`). Each entry must name a ROADMAP item. Entries are strict xfails.
- **SPEC-UNS-3.** Adding a line to the registry, or relaxing a test to make it pass, is a test change and
  is governed by AGENTS.md section 13.

## 9. Non-goals for v1.0

- CUDA, OpenCL/ROCm, distributed training (`tree_learner=data|feature|voting`), and Dask are P8 items. They
  are behind cargo features and do not block v1.0.
- Bit-identical output across different CPU architectures is not a goal. Parity is defined per platform
  (SPEC-SCOPE-3).
